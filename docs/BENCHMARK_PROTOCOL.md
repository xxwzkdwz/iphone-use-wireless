# Appium 与无线直连 WDA 对照协议

使用同一台已解锁 iPhone、同一 Wi-Fi、同一已安装 WDA 和系统设置页面，比较两个后端。原 Appium 版本和实验版使用独立源码、独立配置目录，顺序持有同一设备锁。脚本不会启动原版 Appium；它必须已经正常运行。

```sh
uv run python scripts/benchmark-backends.py \
  --baseline-source /path/to/original-repository \
  --baseline-home /path/to/original-private-state \
  --candidate-home /path/to/direct-private-state \
  --output /path/to/new-private-benchmark-directory \
  --blocks 4 --samples 8 --screenshots 4 --action-cycles 0
```

`--candidate-source` 默认当前实验仓库。输出目录必须为空、属于当前用户且权限为 `0700`；新目录会自动以此权限创建。报告为 `0600`。此命令会连接真实手机并打开系统设置；只做本地静态检查时不要运行它。

## 固定流程

1. 启动前比较两份源码的 `iphone_control.py`、`coredevice_discovery.py`、`state.py` SHA-256，任何差异立即停止。
2. 四块依次为 **Appium → Direct → Direct → Appium**，每块是独立工作进程和独立会话。允许以四的倍数扩展，顺序不变。
3. 通过各自源码的同一 `PhoneService.call` 工具 API 检查准备状态、连接、打开系统设置。模型思考和 MCP stdio 传输不计入。
4. 组件观察热身两次、截图热身一次，然后组件观察八次、截图四次。热身单独标记，不计入正式观察统计。
5. 每块结束前再次审计设置，并显式断开、确认设备所有权已释放。

不重试失败样本，不补测、不静默恢复。任意工具、证据校验或清理失败都会记录并停止后续块；已失败的时间不能冒充成功样本的延迟。超时先请求工作进程退出并清理；强制终止后本轮无效，必须检查设备所有权记录。

## 必须对齐的实际 WDA 设置

Appium 的 `/appium/settings` 可能返回自身设置缓存，因此本协议直接读取**实际 WDA HTTP 端点**：先 `GET /status` 验证预期 Runner 与活动 WDA 会话，再用返回的 WDA session ID 读取 `/session/{id}/appium/settings`。不把 Appium session ID 当成 WDA session ID。

原版默认 WDA 转发端口为 `8100`，可通过 `--appium-wda-port` 指定；直连使用实验配置的本机端口。审计仅在本工作进程持有设备会话时进行，全程只读。它的额外请求和耗时单列为 settings audit，不混入观察样本。

报告保存固定白名单标量设置、所有设置键名，以及全部标量值的本轮 HMAC。重点包括 `waitForIdleTimeout`、`animationCoolOffTimeout`、`snapshotMaxDepth`、`screenshotQuality`；同时检查其他有效标量值。每块开始必须与第一块一致，块内前后也必须一致；不一致即停止并标记不可比，脚本不会修改参数来掩盖差异。未知设置值只进入 HMAC，不把其正文写入报告。

同时检查设备配置指纹、WDA 编译信息、iOS 版本、Python 依赖版本、窗口与截图尺寸。组件必须完整且非空，截图必须为有效签名和合理尺寸的 PNG。报告只保存元素数量、结构/内容 HMAC、PNG 尺寸和字节数；不保存控件正文、完整 XML 或图片。

## 可选操作循环

`--action-cycles 1` 或 `2` 在每块增加少量同流程操作：从实际观察到的唯一搜索框进入搜索，输入固定查询“通用”（不含回车），核对输入值；点击实际观察到的唯一“清除文本”按钮，再点击“关闭”或“取消”；确认键盘收起，向上、向下各滑动一次。

每一步都使用新观察返回的组件引用，并计入默认操作后观察的完整工具耗时；不猜控件 ID，不选择搜索结果，不改变系统设置。预期控件不唯一或不可见时停止，不换用坐标绕过。向上滑动仅核验返回了有效观察；向下滑动还必须确认搜索已关闭、键盘已收起，并恢复本轮开始时的页面结构，不声称固定滚动距离。如果两后端向上滑动后的结构不同，上滑终点与下滑起点就不一致，两个滑动步骤都不能比较速度；即使下滑最终恢复了相同页面，也不能抵消起点不同的影响。每后端只有两块、每块一轮时，每种动作仅 `n=2`，只用于描述，不能泛化为稳定性能结论。

## 如何读报告

- `benchmark.json` 汇总完整计划、各块结果、可比性与停止原因；`block-*.json` 保存每个样本。
- 每块分别报告各操作成功/失败数、中位数和 P90。P90 使用排序样本间线性插值；样本较少时只是描述性分位数。
- 准备检查、连接、打开 App、设置审计、热身、组件观察、截图、动作、断开全部分开统计。连接项反映各后端当前启动与复用生命周期的产品端到端成本，不是纯转发开销；不可把连接时间混进常规操作延迟。
- 请求分段来自 Python `controller.request` 边界，记录脱敏路由、请求数及耗时。它**不表示 Appium 内部实际请求 WDA 的次数，也不能证明内部没有缓存命中**。原始设置审计的请求另标为 `wda_audit_http`。
- 组件结构或数量变化、设置不一致、屏幕方向或截图尺寸变化、源代码/依赖/WDA 信息不一致都会标记不可比。动作样本还单独比较同一步骤观察到的结构，最后必须恢复开始时的页面结构。时钟、电量变化可能改变文本或 PNG 哈希，因此它们单独列出，不能仅凭 PNG 文件哈希不同断言截图质量不同。
- 本协议测量的是现有产品后端的完整工具实现差异，包括连接复用、缓存和转换路径；不能把全部差值直接归因于“去掉 Appium 一层”。

本轮不测试跨网络、锁屏、长时间断线恢复，也不包含模型决策时间。保持手机页面、网络和后台负载稳定，运行时不要手动操作手机或让其他手机控制任务同时运行。
